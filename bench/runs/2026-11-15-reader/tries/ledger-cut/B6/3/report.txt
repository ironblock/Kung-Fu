I wrote /tmp/claude-0/-home-user/00000000-0000-0000-0000-000000000000/scratchpad/reader-work/ledger-cut/B6/3/app/src/chase-camera.ts. It exports createChaseCamera(eye, target) returning { camera, bank(up) } and the ChaseCamera interface as specified. The camera is built with the library's createBankedFreeCamera, and bank() writes the unit up vector into camera.upVector, which lets the library project it onto the view plane. A call whose up is parallel or antiparallel to the line of sight (sin below 1e-9, a threshold kept above the library's own 1e-10 identity-fallback cutoff) returns without touching the roll, so the previous roll is kept.

I checked this with a temporary vitest file against the pinned checkout (six cases: upright start, tilted up, exact parallel and antiparallel, float-noise near-parallel, oblique view with the exact projection, and parallel on an oblique view). All six passed, and I then deleted that file. tsc reports no errors under src/; the only errors come from the library checkout's own XR typings.

Not sure of: if the caller moves camera.position or camera.target directly, a previously stored up can become parallel to the new line of sight. The library then falls back to identity, which is not the previous roll, and bank() cannot recover the old roll from that state. I did not handle this because bank() only receives the up vector. I also did not use any of the ledger's "is" notes; they are unverified and did not bear on the roll math.
