How it works: the camera is built with the library's createBankedFreeCamera (exported in babylon-lite's index.ts, and it is a FreeCamera), and bank() writes the car's up, projected perpendicular to the line of sight, into camera.upVector. When the up is parallel to the line of sight (sine below 1e-6), it re-projects the last picture-up onto the current sight line instead, so the roll is kept. Without this, the library's own look-at would fall back to an identity rotation, which is why I did not just pass the up through.

What I checked against the ledger: the run rows are tool-checked, but I read the source directly rather than trusting the "is" notes. The upVector write path (ObservableVec3 setter, then _markLocalMatrixDirty, then worldMatrixVersion bump) and the view-cache key are as the notes describe, and a test confirms the view matrix changes on a roll. I did not rely on the ledger's notes about yaw/pitch, the fly driver, or viewport, because this module uses neither the controls nor those paths.

Not certain about: the parallel threshold (1e-6) is my choice; an up within about 6e-5 degrees of the sight line counts as parallel. If the car's up is only accurate to float32 precision, that is the right order of magnitude, but it is untested with real car data. Also, if the sight line changes in the same frame that the up goes parallel, the fallback reuses the old roll with the new sight line, which is untested. I also did not verify the right-handed (_rightHanded) mode, because I assumed it leaves the picture-up column unchanged, which I read from the code but did not test.
