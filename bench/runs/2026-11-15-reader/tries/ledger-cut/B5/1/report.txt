It exports `labelPosition(camera, canvas, point)` with the requested signature. It calls the library's own `getViewMatrix`, `getViewProjectionMatrix`, `getEffectiveAspectRatio` and `projectWorldToScreen`, and uses `!offscreen` for `visible`. `offscreen` ignores depth, so points beyond the far plane count as visible, and behind-camera or off-picture points are not. When `camera._useFloatingOrigin` is set, it passes the camera position as `worldOrigin`. Canvas CSS size comes from `clientWidth`/`clientHeight`, falling back to the backing size. A zero-size canvas returns `{x:0, y:0, visible:false}`. No other files were changed. The temporary test I used was deleted.

Checks: a throwaway vitest run gave the expected results for a perspective free camera (centre visible, point behind not visible, point beyond far visible, far-off-screen point not visible), for a floating-origin camera at (50000, 0, 50000) (matches the non-FO result to about 0.03 px), and for an orthographic camera after `enableOrthographicCamera`. `tsc --noEmit` reports no errors in app/src; the errors it does print are pre-existing ones in the library's `?raw`/worker imports and WebXR typings.

Things I was not sure of:
- Points between the eye and the near plane are reported as visible when they fall inside the picture's x/y bounds, because near clipping is not part of the spec's definition. If you want them hidden, that is a one-line change.
- For points behind the camera, x/y are not meaningful (they come out near the centre), so do not use them for edge arrows.
- I assumed the camera's viewport is full, as you said. I used the library's aspect helper, which only differs if `camera.viewport` is partial.
