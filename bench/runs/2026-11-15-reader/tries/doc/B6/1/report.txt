I wrote /tmp/claude-0/-home-user/00000000-0000-0000-0000-000000000000/scratchpad/reader-work/doc/B6/1/app/src/chase-camera.ts. It exports `ChaseCamera` and `createChaseCamera(eye, target)` as specified. It is built on the checkout's `createBankedFreeCamera` (exported from index.ts; the doc and source agree), which builds the basis as x = cross(up, z), y = cross(z, x). The `bank(up)` method passes the component of `up` perpendicular to the line of sight into `camera.upVector`, so the picture-up matches it as closely as possible. When `up` is parallel to the line of sight (within 1e-9 relative), it returns without touching `upVector`, so the previous roll is kept. This avoids the library's identity-rotation fallback, which would reset the roll.

Verification: a temporary vitest file (since removed, so only chase-camera.ts remains) passed 5 cases: initial upright orientation, roll matching the perpendicular component, the parallel case keeping the previous matrix exactly for both `+fwd` and `-fwd`, a degenerate call at start, and a 180-degree flip. `tsc --noEmit` shows no errors in the app sources (the library's own XR files have unrelated type errors).

Not sure of: (1) the 1e-9 parallel threshold is my choice; near-parallel input closer than that is noisy, and I did not test the behavior between 1e-9 and 1e-6. (2) If the eye-to-target line is exactly vertical at creation, the library's identity fallback applies from the start, so the initial view has world +Y as picture-up only by the library's convention. (3) `worldMatrix` is Float32, so exact-match assertions are only accurate to about 1e-7. I did not add a test file to the app.
