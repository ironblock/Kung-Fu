I wrote /home/user/work/b8bdd9/app/src/label-position.ts. It runs the point through the library's own `getViewMatrix(camera)` and `getProjectionMatrix(camera)`. It decides "in front" from view-space z > 0 (that works for both perspective and orthographic) and "inside the picture" from clip x/w and y/w being within [-1, 1]. It never looks at clip z, so mountains past the far plane still count as visible. It then converts to CSS pixels from the canvas's top-left using `getBoundingClientRect()`. Points in front but off-screen get coordinates past the edge. For points behind the camera I divide by |w| so the coordinates stay on the side the point is on, and `visible` is always false. Nothing has been compiled, run or tested, because the library isn't on this machine.

What I'm not sure of:
- **Function signatures.** The ledger names `getViewMatrix` and `getProjectionMatrix` but not their parameters or return types. I assumed each takes just the camera, which fits the cache keys in the ledger: they cover only the transform, fov, near and far, not the canvas shape. I also assumed they return either a 16-number array or an object with an `.m` array.
- **Matrix layout.** I assumed Babylon's usual layout: left-handed, camera looking down +z, translation in elements 12 to 14. That fits the ledger's note that turning ortho off zeroes elements 12, 13 and 15, but no checked row confirms it.
- **Floating origin.** If a scene turns this on (`_useFloatingOrigin`), the view matrix may be measured from a shifted origin. Plain world coordinates would then land in the wrong place. The ledger doesn't say, so I didn't handle it.
- **Near plane.** A point between the camera and its near plane counts as visible, because you only asked for "in front of the camera".
- **Viewport.** `camera.viewport` is ignored, since you said the camera renders to the whole canvas.
