I wrote /home/user/work/0fdbb9/app/src/label-position.ts. It projects the point through `getViewProjectionMatrix(camera)` and treats a point as in front when clip w > 0. It counts the point as visible when it is in front and its NDC x and y are inside [-1, 1]. It never tests depth, so points past the far plane still count as visible. It converts the result to CSS pixels with `canvas.clientWidth`/`clientHeight`, with y measured down from the top. For points behind the camera it divides by |w|, so the x and y stay on the correct side for an arrow. Nothing here could be compiled or run, because the library isn't on this machine (the tsconfig path `../babylon-lite/...` is missing).

What I'm not sure of, because the ledger doesn't cover it:
- **The getter itself:** the ledger only shows that `getViewProjectionMatrix` is defined in camera.ts and refreshes the change key, so fov/near/far edits are picked up. It doesn't say whether the function is exported from `@babylonjs/lite`, whether it takes only the camera, or what it returns. I assumed it takes just the camera and returns a 16-number array (or an object with `.m`) in Babylon's usual layout, with translation in elements 12 to 14.
- **Floating origin:** the scene can switch a camera into floating-origin mode, and when that happens the camera's matrices are rebuilt. If the matrix is then relative to the camera instead of world space, labels will be offset by the camera's position. If that mode is ever on for you, this needs checking.
- **Aspect ratio:** I assumed the projection matrix already uses the canvas's aspect ratio.
- **Orthographic cameras:** w doesn't change with distance, so it can't tell front from behind. Instead the code works out depth from clip z, `nearPlane` and `farPlane`, assuming depth runs 0 at near to 1 at far. If the library uses reversed or GL-style depth, the in-front test is wrong for orthographic cameras. Perspective cameras aren't affected.
- **`camera.viewport`:** I ignored it, since you said the camera renders to the whole canvas.
