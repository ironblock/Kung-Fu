I wrote `/home/user/work/805e4f/app/src/globe-tilt.ts`. Nothing has been compiled, run or tested against the library, since it isn't on this machine.

`tiltGlobeCamera` first loosens the camera's limits so they allow the requested tilt at any zoom: it raises `pitchMax` or lowers `pitchMin` if they are in the way, and pushes any "pitch turned off when zoomed out" radius range out to infinity. Only then does it set `camera.pitch`. Because the loosened limits stay in place, later zooming in or out shouldn't flatten the tilt. After setting the tilt, it checks the result and throws an error if the tilt isn't what was asked, if the zoom, heading or centre moved, or if the camera's position isn't at that angle from the centre.

What I'm not sure of:
- **Setting pitch through `camera.pitch`.** The ledger's only guide to the geospatial camera is a note someone wrote from reading the code, and no tool has checked it. It says writing yaw, pitch or radius rebuilds the camera's position and matrix and clamps the values to `camera.limits`, and that changes to the limits only apply at the next such write. My order of steps (limits first, then pitch) relies on that note being right.
- **Limit field names.** The ledger doesn't name any fields on `camera.limits`. I guessed `pitchMin`, `pitchMax` and `pitchDisabledRadiusScale` from the full Babylon.js library, and the code only touches a field if it exists. If 1.39.0 has some other zoom-dependent pitch rule, the fully-zoomed-out case will fail. It will throw an error rather than leave the camera at the wrong tilt without telling you.
- **The position check.** The angle check assumes the globe is centred at the world origin. If your scene doesn't do that, this check could throw even when the tilt is correct, and you'd want to drop it.
- **Effect on the rest of the app.** Loosening the limits changes how the camera behaves for everything else too. For example, any built-in rule that flattens the view as you zoom out is turned off for good.
