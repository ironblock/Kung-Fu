I wrote /home/user/work/700904/app/src/limited-orbit.ts. It calls the library's `attachControl(camera, canvas, scene)` to get the usual orbit, wheel and pinch controls, and clamps `camera.radius` into range as soon as it is called. It also adds its own clamp to the end of `scene._beforeRender`, after the hook `attachControl` adds. The function it returns takes that clamp out of the list and calls the remover that `attachControl` gives back. Nothing has been compiled or run, because the library isn't on this machine.

**Why it hooks in that way:** I did not use `onBeforeRender`. The ledger checks that it puts callbacks at the start of the frame list, while the camera controls put theirs at the end. A clamp registered there would run before that frame's zoom step, so a hard scroll could leave the camera out of range for that frame. Adding the clamp at the end of the list, after the controls' hook, makes it run after the zoom step. The catch is that this relies on `_beforeRender`, an internal field, through a type cast.

**What I'm not sure of:**
- **`attachControl` details:** the ledger shows the function exists and adds a per-frame hook when given a scene. It doesn't say what order its arguments go in, what it returns, or that it's exported from "@babylonjs/lite". I guessed `(camera, canvas, scene)` and that it returns a function that removes the controls. If it returns nothing, the canvas listeners would stay after removal, so please check this against the real types.
- **Distance means `radius`:** I treated the camera's distance from its orbit point as `camera.radius`.
- **Later hooks:** anything added to the frame list after this call that changes the radius would run after my clamp. For example, an `interpolateArcRotateCamera` animation started later.
- **Removing during a frame:** the remover takes the clamp out of the list straight away. That's safe when called outside the frame loop. The ledger's unchecked note says removing an entry during the loop makes the next hook miss that frame.
- **A built-in alternative:** the library has `setCameraLimits`, which clamps inside the camera's setters and would avoid relying on hook order. The ledger says nothing about its arguments or how to undo it, so I didn't use it. It may be the cleaner choice if you can check how it's called.
- **Bad ranges:** the function throws a `RangeError` if the range isn't valid (not a finite number, negative, or min above max). You didn't ask for that.
