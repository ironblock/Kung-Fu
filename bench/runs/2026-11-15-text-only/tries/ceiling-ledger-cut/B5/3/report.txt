I wrote /home/user/work/d57525/app/src/label-position.ts. It takes the camera's view-projection matrix from the library's `getViewProjectionMatrix` and applies it to the point. A positive clip w means the point is in front of the camera. The point counts as visible when it is in front and its x and y land inside the picture. I never test depth, so points past the far clipping distance still count as visible. x and y are converted to CSS pixels using `canvas.clientWidth` and `clientHeight`. Nothing has been compiled or run, because the library isn't on this machine.

Things I was not sure of:
- **The getter.** The ledger says a function called `getViewProjectionMatrix` exists in camera.ts. It doesn't say whether "@babylonjs/lite" exports it, what arguments it takes, or how the matrix is laid out. I assumed it is exported, takes just the camera, and uses Babylon's usual layout (translation in m[12..14]). I also assumed y points up on screen with no extra flip.
- **Floating origin.** The ledger shows that switching floating origin on or off forces this matrix to be rebuilt, so it probably depends on that mode. If the matrix is camera-relative in that mode, points would need the camera position subtracted first. The ledger doesn't say what the field for that position is called, so I didn't handle it. Labels may be wrong when floating origin is on.
- **Window resizing.** The checks that decide when the matrix is rebuilt look at fov, near plane, far plane and the camera transform, not the canvas aspect ratio. Labels might be off for a frame after a resize. I can't tell, because the ledger doesn't say where the aspect ratio is set.
- **Orthographic cameras.** clip w is always 1, so every point counts as in front of the camera. The code is only right for perspective cameras.
- **Timing.** The ledger has an unchecked note saying `onBeforeRender` callbacks run before the camera controls each frame. If that's true and you position labels there, they would trail the camera by one frame.
- **Points behind the camera.** Their x and y are divided by |w|, which keeps them on the side the camera would turn toward, for an arrow. They are never visible.
- **Viewport.** As you described, I ignore `camera.viewport` and treat the whole canvas as the picture.
