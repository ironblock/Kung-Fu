I worked this out from the standard ArcRotate convention, `position = target + radius·(cos α·sin β, cos β, sin α·sin β)`, because the declarations don't define the position math. Negative beta puts the eye on the far side of the top (equivalent to alpha + π with beta +0.5), and with world up (0,1,0) the picture stays upright. I could not write `notes/over-the-top.json` to disk because I have no file-writing tool in this session, so save the content above yourself. I'm not certain of three things: that Lite uses this convention, that it doesn't clamp or flip the up vector when beta is set directly, and that the two views match bit-for-bit. The fresh camera's z comes out around 6e-16 rather than exactly 0 because of floating-point error in sin(π), so "exactly the same" holds mathematically but not strictly in floats. Checking the library source, or running the two cameras once you have the library, would settle these.
