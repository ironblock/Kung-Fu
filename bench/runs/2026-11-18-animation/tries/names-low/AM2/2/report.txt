I set the weight immediately via `setAnimationWeight`, then issued a zero-duration `fadeAnimationWeight` targeting the same value so that any in-progress fade on this group is replaced by a no-op that completes instantly, leaving the weight locked at `share` for all subsequent frames while other groups' fades are untouched. I was not fully certain that the library's fade implementation replaces (rather than stacks) a prior fade on the same group when `fadeAnimationWeight` is called again; if it stacks, the zero-duration call would still converge to `share` but an old fade might briefly interfere on the very next frame—so if you see a one-frame glitch in practice, the safer fix would be to also track and cancel the fade task externally.
