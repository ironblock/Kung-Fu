I wrote `notes/backward-door.json` with the four computed values based on the tick/seek/loop semantics implied by the type declarations. I was not 100 % certain whether the implementation clamps `currentTime` to exactly 0 on the boundary tick (vs. leaving it slightly negative and sampling at the clamped value), but since both produce the same angle here (the key at t=0 is 0), the numeric answers are unaffected; the only assumption that could shift a result is if the library treats the lower bound differently under `loop: true` (e.g., wrapping via modulo on the *frame* index rather than the *time* value), which would not change the 87.75 answer at this precision either.
