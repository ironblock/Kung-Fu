I implemented `freezeForPosing` by saving the group's `currentTime`, calling `stopAnimation` (which halts all writes to node targets and resets time to the start), then restoring `currentTime` so the group remembers where it was. The returned `resume` closure restores that time and calls `playAnimation`, which re-arms the group so the animation manager drives the nodes again at the group's existing `speedRatio`.

I was not sure whether `playAnimation` on a stopped glTF group that has `loopAnimation: false` and is already at its end would immediately re-stop (analogous to note 8 for property groups), but since we're resuming from a mid-clip `currentTime` that's within range, this shouldn't be an issue in practice.
