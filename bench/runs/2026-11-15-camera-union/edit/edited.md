# Notes on how the camera code of Babylon Lite 1.39.0 behaves

1. attachControl without a scene moves nothing on drags or wheel: they only add to the camera's inertial offset fields (inertialAlphaOffset, ...), applied by the scene._beforeRender hook that any attachControl given a scene for that camera pushes. A two-finger pinch still writes radius at once.
2. Arc-rotate keys feed the inertial offsets only in the frame step of the attachControl they were passed to, so held keys on an attachControl given no scene add nothing, even while another attachControl with a scene drives the same camera.
3. Limit fields set by hand clamp nothing until setCameraLimits runs (interpolateArcRotateCamera clamps its goals to them anyway). setCameraLimits clamps the pose at once; then, until the function its latest call returned runs, a write changing alpha, beta or radius re-clamps each of the three past a field as it is then.
4. NaN is never clamped. The re-clamp runs after attachControl's frame-step clamps (beta to [0.01, PI-0.01], radius >= 0.01): the narrower range holds, and an upper beta or radius limit below 0.01 wins.
5. The re-clamp also clamps interpolateArcRotateCamera's writes, without rejecting: an interpolation whose shortest arc leaves the alpha limits (alpha 0.1 to 6 within [0, 6.2]) stalls at the bound and never settles.
6. Of the clamps, only setCameraLimits' (at its call and on re-clamps) zero an inertial offset, and only that of the channel that hit a bound (inertialRadiusOffset, inertialBetaOffset or inertialAlphaOffset; never the pan offsets). attachControl's beta clamp and 0.01 radius floor zero none, so the offset keeps pushing.
7. Keep each lower limit at or below its upper one: crossed limits make the clamp recurse into a RangeError, thrown by the setCameraLimits call that crosses them or, for fields crossed by hand later, by the next write that changes alpha, beta or radius, wherever it runs.
8. Assigning a new object to ArcRotateCamera.target marks nothing dirty, nor do writes to it (attachControl pans and interpolateArcRotateCamera write camera.target in place): once worldMatrix was read after the last change (getViewMatrix, getCameraPosition), they show at the next changing alpha/beta/radius write.
9. cam.radius = cam.radius is no change. Writes to x/y/z of the target object createArcRotateCamera made mark the camera dirty at once, even after another object was assigned; the view then uses whatever camera.target is.
10. createArcRotateCamera sets nearPlane 0.1, farPlane 1000 and panningSensibility 50 (fov 0.8, angularSensibility 1000, wheelPrecision 3, inertia and panningInertia 0.9).
11. attachFreeControl and attachConfigurableFreeControl aim from FreeCamera._yaw/_pitch (createFreeCamera sets _yaw = atan2(dx, dz); 0 looks along +Z). Each frame of their scene with move or turn velocity (glides too) puts target 1 unit ahead along them, replacing a hand-set target; a hand-written _yaw shows only then.
12. interpolateArcRotateCamera rejects if, at one of its later frames, alpha, beta, radius or target.x/y/z differ from what it last wrote (a second interpolation included); a change undone before that frame does not count. A change before its first frame becomes the start; that frame zeroes all five inertial offsets.
13. By default, GeospatialCamera pitch is free up to pitchMax at radius <= 2*planetRadius, forced to pitchMin (0.001) at >= 4*planetRadius, linear between. The camera starts at 4*planetRadius (or 10 if larger): set radius before pitch, or both in one call.
14. Each re-orbit clamps the pitch, asked for or current, against the radius asked for in that call (the current one if none), before radiusMin/radiusMax clamp that radius. So a radius write that raises it lowers pitch for good: a smaller radius written after does not bring it back.
15. An ArcRotate camera has no beta limits by default; attachControl's frame step clamps beta to [0.01, PI-0.01], but only on frames where inertialAlphaOffset or inertialBetaOffset is non-zero. beta = 0 written directly stays 0.
16. attachControl's keyboard option acts only if enableArcRotateKeyboardControls() ran before that attachControl call; keyboard omitted or false means no keys. Keys are heard on the canvas (tabIndex set to 0 if it has no tabindex attribute) and matched by KeyboardEvent.code; blur clears held keys.
17. In attachControl's keyboard.keys, a list given for one direction replaces that direction's arrow (left: ['KeyA'] stops ArrowLeft); directions not given keep their arrows, and event.ctrlKey and event.altKey act on listed keys as on arrows.
18. flyGeospatialCameraToAsync never rejects. It resolves at a newer flight or, only while the scene runs frames, at its end or the frame after attachGeospatialControls pan, rotate or zoom input (a deltaY 0 wheel is none); if disposeScene clears frames mid-flight it stays pending. Stopped early, it moves no further.
19. During a geospatial flight, direct writes to yaw, pitch, radius or center and setGeospatialOrientation do not stop it: its next frame sets all four again from its own start and goal, overwriting them.
20. Writing GeospatialCamera.center.x/y/z in place moves no eye at once; the next yaw/pitch/radius write that changes the value orbits the changed center. Assigning any object to center (even camera.center itself) or calling setGeospatialOrientation re-orbits at once; the assigned object is copied.
21. enableOrthographicCamera defaults halfHeight to 1; null planes are +-halfHeight vertically and +-halfHeight*aspect horizontally; fov's value is unused (a fov write still rebuilds). A changing write to a field of the bounds it returned acts at that camera's next getProjectionMatrix, while it is camera.ortho.
22. Field writes to an ortho bounds object made by hand (not one enableOrthographicCamera returned for that camera) invalidate nothing. Once enableOrthographicCamera has run on some camera, they show at the next change of fov, nearPlane, farPlane, aspect or view, or of a field of any bounds it returned for that camera.
23. resolveCameraViewport counts camera.viewport.y from the bottom but returns y from the top: {x:0,y:0,width:0.5,height:0.5} on 800x600 gives {x:0,y:300,width:400,height:300}. Edges are clamped to the canvas: {x:-0.5,width:1} gives width 400.
24. attachControl acts only on button 0 and 2, by default rotate and pan, as pointerMappings set them for mouse and pen: a middle-button drag does nothing and Ctrl changes nothing. A one-finger touch pointer always rotates; while two touches are down pointer moves do nothing and the pinch only zooms.
25. disposeScene removes none of the listeners that attachControl, attachFreeControl, attachConfigurableFreeControl or attachGeospatialControls (keys on window) add. Each one's returned function does; so does disposeScene if that function was registered with onSceneDispose(scene, fn).
26. In attachConfigurableFreeControl, upKeys and downKeys replace the defaults (upKeys ['KeyE'] makes Space do nothing). fastMultiplier defaults to 1, so fastKeys alone do not speed anything up.
27. Projection is reverse-Z, perspective and orthographic alike: getProjectionMatrix maps nearPlane to depth 1 and farPlane to depth 0, so the z of projectWorldToScreen is 1 at the near plane and 0 at the far plane.
28. attachControl's wheel does inertialRadiusOffset -= deltaY*radius/(wheelPrecision*1000) and each frame radius -= that offset, so positive deltaY zooms out. Frames with inertialRadiusOffset != 0, and the pinch, floor radius at 0.01 (a smaller upperRadiusLimit wins); a direct write below 0.01 stays until such a frame.
29. A pan drag (button 2 by default) adds -dx/panningSensibility to inertialPanningX, dy/panningSensibility to inertialPanningY. Per frame, if 0 < beta < PI, the target moves inertialPanningX*radius/1000 along the right vector (-sin(alpha), 0, cos(alpha)), negated in a right-handed build; then both decay by panningInertia.
30. The same frame moves the target inertialPanningY*radius/1000 along the up vector (-cos(alpha)cos(beta), sin(beta), -sin(alpha)cos(beta)). For beta outside (0, PI): where |sin(beta)| < 1e-10 (PI, -PI, 2*PI) both go along world +X and +Y; at beta 0 sin(beta) counts as 0.0001; elsewhere both flip where sin(beta) < 0.
31. createGeospatialCamera starts at center (planetRadius,0,0), yaw 0, pitch 0.001, radius 4*planetRadius (10 if that is smaller), nearPlane 1, farPlane 16*planetRadius; limits radiusMin 10 (any planet size), radiusMax 4*planetRadius, pitchMax PI/2-0.01.
32. If 4*planetRadius < 10 the camera starts at radius 10, and every re-orbit (a yaw, pitch or radius write that changes the value, a center assignment, setGeospatialOrientation) turns a radius of 10 or more into 4*planetRadius and a smaller one into 10, so the radius alternates.
33. attachGeospatialControls hears keys on window, not the canvas, and leaves tabIndex alone. A left drag pans the center if the press hits the planet sphere, else does nothing; any other button's drag rotates with no coasting, yaw += dx*PI/500 and pitch += dy*PI/500, pitch clamped to [0, PI/2-0.001] before the limits.
34. attachControl's two-finger touch pinch (touchstart/touchmove events) sets radius to start radius * start distance / current distance, at least 0.01 (an upperRadiusLimit below that still wins), at once: before any frame runs and with no inertial offset.
35. Calling enableOrthographicCamera again replaces camera.ortho with fresh bounds; the old object no longer drives the projection. disableOrthographicCamera sets camera.ortho to null and clears the cached ortho terms; a hand-written camera.ortho = null keeps them.
36. projectWorldToScreen and its ToRef form: a point behind the camera has behindCamera, offscreen and clipped true; one in frame but past farPlane or nearer than nearPlane only clipped. x/y are not clamped. A point on the camera plane gives NaN under perspective (clipW 0); under ortho clipW is 1 and x/y stay finite.
37. In attachFreeControl and, by default, attachConfigurableFreeControl, KeyW/ArrowUp and KeyS/ArrowDown move along the look direction with pitch, KeyA/KeyD and ArrowLeft/ArrowRight sideways, Space/PageUp up world Y, ShiftLeft/ShiftRight/PageDown down. Keys are heard on the canvas (tabIndex 0 if no tabindex attribute).
38. projectWorldToScreen and its ToRef form give x/y in canvas backing pixels (plus viewport.x/y, y down), z reverse-Z (1 at nearPlane, 0 at farPlane), cssX = x*cssWidth/backingWidth, cssY likewise (x, y if no css size is given). RangeError if a viewport or backing size is not finite and > 0, or one css size comes alone.
39. In attachFreeControl and attachConfigurableFreeControl each frame a held move key adds speed*max(deltaMs,1)/sqrt(100000) (times fastMultiplier while a fastKeys key is held) to the move velocity, which decays by inertia once per frame whatever deltaMs and is zeroed below speed*0.001. A 0 ms frame moves as 1 ms does.
40. createFreeCamera has no upVector and always builds its basis on world +Y; only createBankedFreeCamera has upVector. Writing it rolls the camera, unless it is zero or parallel to the view direction: then the camera turns to look along +Z.
41. attachFreeControl and attachConfigurableFreeControl given no scene never move the camera: all motion is applied in their _beforeRender step.
42. Each frame interpolateArcRotateCamera moves 1 - 2^(-dt/interpolationFactor) of the remaining way (for alpha and beta, of the shortest arc), dt being the frame delta in seconds (a delta <= 0 counts as 1/60 s) and the factor 0.1 by default; a factor <= 0 snaps on the first frame.
43. setCameraLimits writes only the fields present in its argument, so calls add up; a field passed as undefined removes that bound. Only the function returned by the latest call stops the clamping, and it leaves the limit fields set.
44. A rotate drag subtracts dx/angularSensibility from inertialAlphaOffset, dy/angularSensibility from inertialBetaOffset. Each frame attachControl adds both (alpha's negated in a right-handed build), subtracts inertialRadiusOffset from radius, multiplies the three by inertia: inertia 0 ends rotation and zoom in one frame.
45. getViewMatrix, getProjectionMatrix and getViewProjectionMatrix return the camera's own cache object. A camera write leaves it alone; the next call of that getter by anyone (getViewProjectionMatrix calls the other two) after a change of pose, fov, nearPlane, farPlane, ortho or aspect overwrites it in place.
46. getProjectionMatrix does not apply camera.viewport; pass getEffectiveAspectRatio(camera, width, height) as the aspect to match what is rendered.
47. A GeospatialCamera.limits field change acts at the next yaw/pitch/radius write changing its value, center assignment or setGeospatialOrientation. pitchDisabledRadiusScale null: pitchMax at any radius.
48. A new object assigned to camera.limits is ignored by the camera's own clamps (every yaw/pitch/radius/center apply, the controls' re-centre included) but read live by attachGeospatialControls for zoom distance, the pick sphere and the collision floor.
49. Each frame a held arc-rotate arrow adds 1/angularSensitivity (keyboard option, default 100, not the camera's) to inertialAlphaOffset or inertialBetaOffset: ArrowRight raises alpha (lowers it in a right-handed build), ArrowUp lowers beta. A plain diagonal adds 1/sqrt(2) of that to each.
50. With event.ctrlKey true the arrows instead add 1/panningSensitivity (50) to inertialPanningX/Y, diagonals scaled by 1/sqrt(2). With altKey true, Left/Right add the full 1/angularSensitivity to alpha's offset and Up/Down +-1/zoomingSensitivity (25) to inertialRadiusOffset (Up zooms in), unscaled on diagonals.
51. attachFreeControl and attachConfigurableFreeControl turn on a drag of button 0, 1 or 2, no pointer lock (right drag turns right, down looks down): dx/angularSensitivity feeds a turn velocity, applied then times inertia each frame, until below camera.speed*0.001. Only turning frames clamp _pitch to +-(PI/2-0.01).
52. So the glide after a free-camera drag depends on speed (default 2) and drag size: at speed 1000 and angularSensitivity 2000 a 200 px drag turns once with no glide, a 3000 px drag still glides.
53. flyGeospatialCameraToAsync times the flight from the frame deltas given to _beforeRender (durationMs default 1000; a delta <= 0 counts as 1000/60 ms) and turns yaw the short way round (3 to -3 passes through PI).
54. createFreeCamera starts with fov 0.8, nearPlane 1 and farPlane 10000, unlike createArcRotateCamera's 0.1 and 1000.
55. A bounds object assigned to camera.ortho by hand is ignored (perspective used) until enableOrthographicCamera has run on any camera; then it is used at the camera's first getProjectionMatrix, else only at the next change of fov, nearPlane, farPlane, aspect, view, or a field of bounds it returned for that camera.
56. interpolateArcRotateCamera moves nothing until a scene frame runs. Each frame it clamps its alpha/beta/radius goals to the limit fields; a NaN alpha, beta or radius goal counts as omitted, a NaN in goal.target is written to camera.target and rejects the promise.
57. interpolateArcRotateCamera ends on the clamped goal; alpha and beta are not wrapped: from alpha 0 a goal alpha of 2*PI is a zero arc, so it ends on the first frame with alpha 2*PI and no visible turn.
58. Assigning camera.ortho = null by hand keeps the cached orthographic matrix, and the perspective rebuild after a fov write still has the ortho p[12], p[13] and p[15]=1. disableOrthographicCamera clears those and switches at the next getProjectionMatrix.
59. attachGeospatialControls zooms by the sign of wheel deltaY only (> 0 zooms out). Zoom coasts with inertia 0.9 per 1/60 s: a wheel step goes about as far at 30 fps as at 60; a held zoom key adds a step per frame, zooming faster at higher rates. Pan and rotation have no inertia and stop on the first frame without input.
60. A geospatial center whose latitude asin(z/|center|) is beyond +-87.13 degrees (0.05 rad from the +-Z pole) is moved to +-87.13 at every re-orbit (center assignment, setGeospatialOrientation, a yaw/pitch/radius write changing it, each control or flight step), keeping |center| and longitude; camera.center reads it so.
61. In attachControl, shouldHandlePointerDown false ignores that press; isExternalDragActive true mid-drag ends the drag and zeroes the rotation and pan offsets (not inertialRadiusOffset); isExternalPickPending true swallows moves, and the drag goes on once it is false.
62. In GeospatialCamera north is +Z: at a center on +X, yaw 0 heads toward +Z and yaw PI/2 (east) toward -Y (+Y in a right-handed build); pitch 0 looks straight down. yaw and pitch are wrapped to [-PI, PI) before the limits clamp them, so yaw = 4 reads 4 - 2*PI and yaw = PI reads -PI.
63. attachGeospatialControls' checkCollisions (default false) lifts center each frame the eye is nearer the origin than limits.planetRadius + limits.radiusMin, by the shortfall along the eye's direction; yaw and pitch then apply in the moved center's frame, so a tilted eye stays short (exact only looking straight down).
64. attachGeospatialControls picks only by a ray against a sphere of limits.planetRadius at the origin: scene meshes never block it. A dblclick with button 0 and buttons 0 that hits it flies center to the hit point over doubleTapAnimationDurationMs (1000); another button, buttons not 0, or a miss does nothing.
65. When camera._useFloatingOrigin is set, getViewMatrix zeroes its translation, so the matrices are camera-relative; projectWorldToScreen then needs worldOrigin at the camera's world position. A cached view is kept until the camera's pose changes; a camera never viewed uses the flag at its first getViewMatrix.
66. In attachGeospatialControls, on the first frame with no pan or zoom step after one (a zoom's steps end when its coasting does), center moves to where the eye's look vector enters the sphere of the current camera.limits.planetRadius, and radius becomes that distance. If it misses, or the eye is inside, nothing moves.
67. That re-centre measures yaw and pitch again at the new center and clamps them and the radius by the camera's own limits object (not one assigned later to camera.limits), pitch against the new radius: the eye moves if the radius is clamped or the pitch is too steep for that radius.
68. A camera from createFreeCamera whose view direction is parallel to world Y (target straight above or below) gets an identity rotation and looks along +Z.
69. A createFreeCamera view is built from position and target alone (a banked camera's also from upVector): moving position keeps it aimed at the target, so it turns; to translate, move target by as much. Such writes leave _yaw/_pitch alone, so attached free controls re-aim at the next key move or drag.
70. Geospatial keys: arrows pan the center north/east by radius*0.0015*min(1, sqrt(cos(latitude))*max(1, |center|/h)) per frame, h = |eye| - |center| (a full step at the equator or near the ground); while ControlLeft or ControlRight is held (not the ctrlKey flag) arrows rotate instead.
71. Geospatial keys Equal/NumpadAdd and Minus/NumpadSubtract zoom in/out along the look vector, keeping the center while the zoom runs (then the re-centre applies).
72. fov, nearPlane and farPlane are plain fields; a write takes effect at the next getProjectionMatrix/getViewProjectionMatrix call, which compares them by value. While camera.ortho is set and enableOrthographicCamera has run once, fov's value is unused, though a fov write rebuilds, so a hand-set ortho then takes effect.
73. getCameraPosition reads the world matrix translation, so it includes the camera's parent transform.
74. Ortho bounds are view-space world units around the camera's view axis; depth still comes from camera.nearPlane and farPlane.
75. A right-handed build resolves the babylon-lite-rh import condition. There attachControl flips the sign of alpha and of horizontal pan, from drags and keys alike, and attachFreeControl and attachConfigurableFreeControl that of the drag's _yaw step, so the view moves the same way on screen; _yaw is still atan2(dx, dz).
76. In a right-handed build attachGeospatialControls flips nothing: a drag adds to yaw and pitch as in a left-handed one. But east, and so yaw PI/2, points the other way there (toward +Y at a center on +X).
77. projectPointToViewportToRef does no validation, multiplies transform by the world matrix into a new matrix on every call (it allocates), accepts zero-size viewports, and writes only x, y, z.
